## ⚠️ The one gotcha that will bite step 6: SwiftData in-memory cascade staleness

This cost real debugging in step 5 and the step-6 spec walks straight into it.

After `context.delete(someLink)` (or `context.delete(person)`), SwiftData does **not** eagerly
remove the deleted `PersonUnionLink` from a related object's in-memory to-many array
(`union.links`, `person.links`) until the context is saved and/or the object is refetched.

Consequences for step 6's `unlink`:
- The spec says "after removing the link, if the union has no remaining `.partner` links, delete
  the union." Counting partner links on `union.links` **right after** deleting the link will
  still see the just-removed link and skip the prune. **Decide which unions to prune BEFORE
  deleting**, by excluding the link/person you're about to remove — exactly how
  `TreeMutationService.deletePerson` was written in step 5. Copy that shape.
- The spec's `unlinkCleansUpOrphanedUnion` test asserts
  `focal.links.filter { $0.role == .partner }.isEmpty` after the unlink. That inspects the
  **stale in-memory array** and will likely fail even when the store is correct. Assert pruning
  against a persisted fetch instead: `try context.fetch(FetchDescriptor<Union>())`. (Step 5 fixed
  the analogous `deletePersonPrunesOrphanedParentUnion` test the same way — this is an approved
  deviation, not a spec violation. Add `import SwiftData` to the test file for `FetchDescriptor`.)

## Step 6 scope (see spec for full detail)

Connect two people who **already exist** in the tree, and remove connections:

1. `linkAsParent/linkAsPartner/linkAsChild` + `unlink` on `TreeMutationService` (+ protocol).
2. `LinkPersonView` — a 3-step sheet (pick person → choose relationship → review) with its own
   `NavigationStack`, receiving `allPeople` from `TreeTabView`.

4. Swipe-to-delete (unlink) on relationship rows — no confirmation dialog (reversible via
   re-link); the full-person delete keeps its `confirmationDialog` (irreversible).

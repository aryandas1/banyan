## What steps 1–3 already built (do not modify without reason)

**Models (`Banyan/Models/`)** — pure of SwiftUI; `@Model` classes import SwiftData only:
- `Person` — `id, treeId, firstName, lastName, sex: Sex, birthDate/deathDate: PartialDate?,
  birthPlace/deathPlace, isPlaceholder, profilePhotoFilename, bio, createdAt`,
  `@Relationship(.cascade, inverse: \PersonUnionLink.person) links`.
  Computed: `fullName`, `initials`, `isDeceased`.
- `Union` — `id, treeId, type: UnionType, startDate/endDate, endReason`, cascade `links`.
  `init(id:treeId:type: = .unknown, startDate:endDate:endReason:)`.
- `PersonUnionLink` — `id, role: LinkRole (.partner/.child), childType: ChildType?`, plain
  optional `person`/`union` back-refs (**no `@Relationship` on this side** — the inverse is
  declared on `Person.links` / `Union.links`). `init(id:role:childType: = nil)` — `childType`
  already defaults to `nil`, so `PersonUnionLink(role: .partner)` compiles as-is; the step-4
  spec's `makeLink` helper snippet matches this exactly.
- `PartialDate` — Codable struct, `year/month/day/isEstimated`, `.displayString`.
- Enums (`Sex`, `UnionType`, `EndReason`, `LinkRole`, `ChildType`): String, Codable, CaseIterable.
- `BanyanSchemaV1: VersionedSchema` wraps the three `@Model`s.

**`GraphService` / `GraphServiceProtocol` (`Banyan/Services/`)** — pure, no SwiftUI/SwiftData:
`parents(of:)`, `allPartners(of:)`, `children(of:)`, `siblings(of:)` (siblings = share a
parent *union*; half-siblings excluded), `unions(for:)`, `partners(of:in:)`,
`allPeople(treeId:from:)`. `TreeMutationService` (step 4) will sit alongside this and should
follow the same shape: pure Foundation + SwiftData, no `@Observable`, no SwiftUI import.

**`TreeViewModel` (`Banyan/ViewModels/`)** — `@MainActor @Observable`:
- `focusedPersonId: UUID?`, `navigationStack: [UUID]`
- `focus(on:)` (pushes previous focus; no-op if re-focusing current),
  `goBack()` (no-op on empty stack), `resetToRoot(ownerId:)`,
  **`jumpTo(personId:)`** — added post-step-3 during PR review to fix breadcrumb navigation:
  truncates the stack back to the tapped person instead of pushing onto it, falling back to
  `focus(on:)` if the person isn't in the stack. Not in the original step-3 spec — a real
  bug found and fixed in review, so don't be surprised it's there.

**`ThreeGenViewModel` (`Banyan/ViewModels/`)** — `@MainActor @Observable`. Owns the

`init(focalPerson:graphService:)` loads immediately; **`update(focalPerson:)` exists,

`ThreeGenViewModel` on focus change rather than calling `update`. Step 4's spec explicitly
calls for wiring `update(focalPerson:)` into a new `refreshSnapshot()` in `TreeTabView` after
a save — **this is the first real caller of that method**, so pay attention to it working
correctly (see "Wiring" section of the spec).

**Tree UI (`Banyan/Views/Tree/`)** — `ThreeGenView`, `PersonNodeView`, `PlaceholderNodeView`

and reused everywhere (this was hoisted post-step-3 during PR review — don't reintroduce

## Step 4 scope (see spec for full detail)

Wires the placeholder nodes to a real add-person flow. New: `TreeMutationService` (graph
mutation logic — creates a person + wires them into a union/link), `AddPersonViewModel`
(multi-step form state), `AddPersonView` + four step views (Name → Birth → Status → Review)

### Gaps in the spec worth resolving up front

1. **The `makeLink` helper snippet never calls `context.insert(link)`.** Per the existing
   SwiftData rule ("insert before wiring relationships"), every new `PersonUnionLink` must be
   inserted into the `ModelContext` — the spec's prose describes insert order for `addParent`
   (Person → Union → PersonUnionLink) but the code snippet for `makeLink` only sets
   `.person`/`.union` and returns. Insert inside `makeLink` itself (or immediately before
   calling it) so this isn't missed.
2. **`AddPersonViewModel.save(in:)` is `async throws`, but nothing in the spec shows how the
   Review step's Save button calls it or routes a thrown error into `vm.saveError`.** A
   `Button` action is synchronous, so the call site needs a `Task { }` wrapping a `do/catch`
   that assigns `vm.saveError = error` on failure — `save(in:)` itself never touches
   `saveError`. Without this, the spec's "Error handling: `.alert` bound to `vm.saveError`"
   requirement has no code path that actually populates it.
3. **`TreeTabView` no longer matches the step-3 spec's original shape** — it now has a custom
   `init(ownerPersonId:)` (for the shared `graphService`, see above) rather than plain stored
   properties. When adding `@State private var addPersonContext: AddPersonContext? = nil`,
   it's a normal property with a default value — no init change needed for it specifically,
   but don't assume the file looks like the original step-3 prompt's snippet; read the current
   file first.
4. **`onChange(of: allPeople.count)` already exists** in `TreeTabView` (guards
   `threeGenViewModel == nil` and calls `setUpIfPossible()`). The spec's replacement snippet
   (branch to `refreshSnapshot()` when a ViewModel already exists) is a straightforward
   edit to that existing handler, not a new one — don't duplicate the modifier.
